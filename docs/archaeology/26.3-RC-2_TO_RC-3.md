# 26.3-rc-2 → 26.3-rc-3 binary archaeology

## Conclusion

After ordinary release bookkeeping is removed, the published client has exactly three
behavioral change clusters. Together they account for all four fixes in the official
26.3 Release Candidate 3 notes.

| Issue | Class cluster | Implementation change | Confidence |
|---|---|---|---|
| `MC-311456` | `GlDevice` / `GlSurface` | Make the target surface window current before setting swap interval | `HIGH_CONFIDENCE` |
| `MC-311586` | `GlDevice` / `GlSurface` | The same context/window-selection correction applies to both interval `0` and `1` | `HIGH_CONFIDENCE` |
| `MC-311477` | `JoinMultiplayerScreen` | Copy the edited clone's server-pack status back to the saved `ServerData` | `HIGH_CONFIDENCE` |
| `MC-311799` | `RemotePlayer` | Make client-side hit simulation report success so the existing sprint-knockback/attacker-slowdown path runs | `HIGH_CONFIDENCE` |

No non-version executable change remains unexplained. The two VSync issues correspond
to one implementation cluster; there is not a one-bug-to-one-method mapping.

## Evidence boundary and reproduction

The evidence in this report comes from the resolver-verified Mojang JARs and direct
classfile inspection. No RC3 source was decompiled, reconstructed, or compiled.

The main release delta is reproducible with:

```powershell
.\gradlew.bat run --args="diff-bin fixtures/26.3-rc-2.json fixtures/26.3-rc-3.json --side client --details"
```

Unchanged methods cited below can be reproduced by full JVM identity. For example:

```powershell

```

The symbolic snippets are focused excerpts from those commands, not source or a
decompiler rendering.

## MC-311456 / MC-311586 — OpenGL VSync

### Changed members and instructions

RC3 adds a private final, non-synthetic source field to `GlSurface`:

```text
device:Lcom/mojang/renderpearl/backend/opengl/GlDevice;
```

The package-private constructor descriptor changes accordingly:

```text
RC2:
  GlSurface(long windowHandle, BooleanSupplier isIconified)

RC3:
  GlSurface(GlDevice device, long windowHandle, BooleanSupplier isIconified)
```

This is represented in the classfile as one removed constructor and one added
constructor because JVM member identity includes the descriptor. It is a deliberate
API-shape/source-member change, not compiler-generated fallout.

`GlDevice.createSurface` changes only enough to pass its own device reference:

```text
RC2:
  new GlSurface
  load windowHandle
  load isIconified
  invokespecial GlSurface.<init>(J, BooleanSupplier)

RC3:
  new GlSurface
  load this                         // new
  load windowHandle
  load isIconified
  invokespecial GlSurface.<init>(GlDevice, J, BooleanSupplier)
```

The effective change is in `GlSurface.configure`:

```text
RC2:
  interval = configuration.presentMode() == FIFO ? 1 : 0
  SDL_GL_SetSwapInterval(interval)
  swapchainWidth = configuration.width()
  swapchainHeight = configuration.height()

RC3:
  device.makeCurrent(windowHandle)  // new
  interval = configuration.presentMode() == FIFO ? 1 : 0
  SDL_GL_SetSwapInterval(interval)
  swapchainWidth = configuration.width()
  swapchainHeight = configuration.height()
```

The changed conditional branch labels in the detailed diff are consequences of the
five inserted instructions; the FIFO-to-`1`, other-mode-to-`0` logic is unchanged.

### Relevant unchanged state and calls

The `GlDevice` constructor initializes `currentWindow` to zero, creates an OpenGL
context on a separately created window named `Minecraft - RenderPearl OpenGL Hidden
Utility Window`, and calls `makeCurrent(initialWindowHandle)`. Thus the device begins
with its shared context associated with the hidden utility window, not the later game
window surface.

The unchanged `GlDevice.makeCurrent(long)` is:

```text
if requestedWindow == currentWindow:
  return
currentWindow = requestedWindow
SDL_GL_MakeCurrent(requestedWindow, glContext)
```

`GlCommandEncoder.presentTexture`, also unchanged, calls the same
`device.makeCurrent(windowHandle)` before rendering to a surface. In RC2 that call was
too late to select the target window for the earlier swap-interval update. RC3 performs
the association in `configure` itself.

The unchanged option/configuration chain is:

```text
Options VSync listener
  → Minecraft.invalidateSurfaceConfiguration()
  → next renderFrame configuration pass
  → GpuSurface.PresentMode.getSupportedVsyncMode(supportedModes, optionValue)
  → new GpuSurface.Configuration(width, height, presentMode)
  → FrontendGpuSurface.configure(configuration)
  → GlSurface.configure(configuration)
```

For OpenGL, `GlSurface.supportedPresentModes()` returns `{FIFO, IMMEDIATE}`. The
unchanged selector chooses FIFO when VSync is requested and IMMEDIATE when it is not.
`GlSurface.configure` maps those modes to SDL intervals `1` and `0`, respectively.

The unchanged frontend validates that the mode is supported, calls the backend, then
stores the requested `Configuration` as `currentConfiguration`.

### What is and is not synchronized

RC3 consults device state indirectly: `makeCurrent` compares the target surface handle
with the device's internally tracked `currentWindow`, and only calls
`SDL_GL_MakeCurrent` when they differ. It does **not** call
`SDL_GL_GetCurrentWindow`, `SDL_GL_GetCurrentContext`, or
`SDL_GL_GetSwapInterval`.

The new code therefore synchronizes the device's current window/context association
with the surface being configured before applying the requested presentation state.
It does not read back or validate the actual swap interval. Both
`SDL_GL_MakeCurrent` and `SDL_GL_SetSwapInterval` still have their boolean return values
discarded.

SDL's API contract is the relevant external semantic fact: `SDL_GL_MakeCurrent`
associates an OpenGL context with a window for rendering, while
`SDL_GL_SetSwapInterval` sets the interval for the current OpenGL context; interval
`0` is immediate and interval `1` synchronizes with vertical retrace. See the official
[SDL_GL_MakeCurrent](https://wiki.libsdl.org/SDL3/SDL_GL_MakeCurrent) and
[SDL_GL_SetSwapInterval](https://wiki.libsdl.org/SDL3/SDL_GL_SetSwapInterval)
documentation.

### BooleanSupplier

The `BooleanSupplier` is unchanged across the release. `Minecraft` supplies a bound
window-iconification check when creating the surface; `GlSurface` stores it as
`isIconified`; and `acquireNextTexture()` calls it to throw `SurfaceException` with
`Cannot acquire minimized window` while the window is minimized. Neither RC2 nor RC3
uses it to select, query, or apply VSync.

### Conceptual pseudocode — not recovered Mojang source

```java
// RC2 conceptual
final class GlSurface {
    private final long windowHandle;

    void configure(Configuration requested) {
        SDL_GL_SetSwapInterval(requested.presentMode() == FIFO ? 1 : 0);
        rememberSize(requested);
    }
}

// RC3 conceptual
final class GlSurface {
    private final GlDevice device;
    private final long windowHandle;

    void configure(Configuration requested) {
        device.makeCurrent(windowHandle);
        SDL_GL_SetSwapInterval(requested.presentMode() == FIFO ? 1 : 0);
        rememberSize(requested);
    }
}
```

### Behavioral interpretation

In RC2, configuring VSync could apply interval `0` or `1` while the shared context was
still associated with the hidden utility window. The game surface was made current
only later during presentation. The displayed window's effective presentation state
could therefore disagree with the option in either direction.

RC3 binds the game surface first and then applies the interval. Because both enabling
and disabling use the same `configure` path and differ only in the requested interval,
one implementation correction plausibly and directly resolves both `MC-311456` and
`MC-311586`.

## MC-311477 — server resource-pack setting persistence

The actual edit UI class in these binaries is `ManageServerScreen`; there is no
`EditServerScreen.class`. The relevant unchanged methods establish an explicit
edit-clone/copy-back workflow.

When the Edit button is used, unchanged `JoinMultiplayerScreen.lambda$init$3`:

1. obtains the selected list entry's original `ServerData`;
2. constructs a distinct `editingServer` object;
3. calls `editingServer.copyFrom(original)`; and
4. passes the clone to `ManageServerScreen`, with `editServerCallback` as the Save
   callback.

Unchanged `ServerData.copyFrom` copies name/icon, resource-pack status, and type from
the original into the clone. The UI's unchanged resource-pack cycle callback calls:

```text
editingServer.setResourcePackStatus(selectedStatus)
```

The preference is the private `ServerData.packStatus` field, exposed by
`getResourcePackStatus()` and `setResourcePackStatus(...)`. Its values are `ENABLED`,
`DISABLED`, and `PROMPT`.

The focused RC2→RC3 delta in `editServerCallback(boolean)` is:

```text
RC2:
  original.name = editingServer.name
  original.ip = editingServer.ip
  original.setState(INITIAL)
  servers.save()

RC3:
  original.name = editingServer.name
  original.ip = editingServer.ip
  original.setState(INITIAL)
  original.setResourcePackStatus(editingServer.getResourcePackStatus())  // new
  servers.save()
```

RC2 neither replaces the list entry with the clone nor copies the clone's edited
resource-pack status back to the original. It saves the original list object with the
old value. RC3 explicitly transfers the missing state before the same save.

The unchanged persistence path is also direct:

```text
ServerList.save()
  → for each ServerData: ServerData.write()
  → ServerData.ServerPackStatus.FIELD_CODEC
  → optional boolean NBT field "acceptTextures"
  → NbtIo.write(tempFile)
  → Util.safeReplaceFile(servers.dat, tempFile, servers.dat_old)
```

The codec encodes `ENABLED` as `true`, `DISABLED` as `false`, and `PROMPT` as an absent
optional field; reading an absent value defaults to `PROMPT`.

### Conceptual pseudocode — not recovered Mojang source

```java
// Both releases open the editor on a copy.
ServerData editing = new ServerData(original.name, original.ip, OTHER);
editing.copyFrom(original);
openManageServerScreen(editing);

// RC2 conceptual Save
original.name = editing.name;
original.ip = editing.ip;
servers.save();              // serializes original.packStatus, still old

// RC3 conceptual Save
original.name = editing.name;
original.ip = editing.ip;
original.setResourcePackStatus(editing.getResourcePackStatus());
servers.save();              // serializes the edited value
```

This is a one-property omission in the copy-back step, not a change to the NBT format
or save destination. It directly explains `MC-311477`.

## MC-311799 — sprint-attack attacker slowdown

### New override and hierarchy meaning

RC3 adds this public, non-synthetic method to `RemotePlayer`:

```text
RemotePlayer.hurtClient(DamageSource)Z
  constant 1
  return
```

Conceptually it returns `true` unconditionally. It is a deliberate new source override,
not a bridge or other compiler-generated member.

The relevant hierarchy is:

```text
Entity
  └─ LivingEntity
      └─ Avatar
          └─ Player
              └─ AbstractClientPlayer
                  ├─ LocalPlayer
                  └─ RemotePlayer
```

`Entity.hurtClient(DamageSource)` is unchanged and returns `false`. Neither `Player`
nor `AbstractClientPlayer` overrides it. Therefore an RC2 `RemotePlayer` inherited
`false`; RC3 dispatches to the new `true` override.

### Smallest explanatory call chain

The unchanged final method `Entity.hurtOrSimulate` selects real server damage or a
client simulation result:

```text
if level is ServerLevel:
  return this.hurtServer(serverLevel, source, amount)
else:
  return this.hurtClient(source)
```

The unchanged `Player.attack(target)` calls:

```text
successful = target.hurtOrSimulate(damageSource, damage)
if successful:
  causeExtraKnockback(...)
  perform sweep/visual/item/stat/exhaustion success work
else:
  play PLAYER_ATTACK_NODAMAGE
```

For a sprint attack, the same method marks its sprint-knockback condition true and
adds `0.5f` to the target knockback passed to `causeExtraKnockback`. The unchanged
`Player.causeExtraKnockback` executes the following whenever the resulting knockback
is positive:

```text
knock back or push target
attacker.setDeltaMovement(attacker.getDeltaMovement().multiply(0.6, 1.0, 0.6))
attacker.setSprinting(false)
```

The `RemotePlayer` return value is therefore not merely a damage acknowledgement. On
the client it gates the existing predicted attack-success branch containing sprint
knockback, horizontal attacker slowdown, and sprint cancellation.

### Conceptual pseudocode — not recovered Mojang source

```java
// RC2 conceptual dispatch for another client player
target.hurtOrSimulate(source, damage)
    -> Entity.hurtClient(source)
    -> false;

// RC3 conceptual dispatch for another client player
target.hurtOrSimulate(source, damage)
    -> RemotePlayer.hurtClient(source)
    -> true;

if (successfulHit && sprintKnockback) {
    applyTargetKnockback();
    attacker.velocity *= new Vec3(0.6, 1.0, 0.6);
    attacker.setSprinting(false);
}
```

In multiplayer client state, the attacked other player is represented by
`RemotePlayer`. RC2's inherited `false` skipped the success branch, so a sprint attack
did not locally slow/cancel the attacker. RC3's override enters the already-existing
branch. No change to `Player.attack`, `Entity.hurtOrSimulate`, or
`causeExtraKnockback` was required, and those containing classes are byte-identical
between releases. This directly explains `MC-311799`.

## Remaining uncertainty

The binaries do not expose Mojang's source-level commits, developer intent, or the
platform-specific reproduction conditions for the two VSync reports. They also do not
read back SDL's actual swap interval or check the boolean result of either SDL call,
so they do not prove that every driver accepts every requested interval.

They do establish the complete executable delta: RC3 applies OpenGL presentation
configuration after selecting the target surface window, persists the edited server
resource-pack preference, and treats a client-side hit on `RemotePlayer` as successful
so the existing sprint-attack slowdown path executes.
