# 26.3-rc-1 → 26.3-rc-2

## Conclusion

**MC-311782 assessment: `HIGH_CONFIDENCE`.**

RC2 moves the unchanged `SDL_OpenURL` operation out of `Blaze3D.openUri` and into a synthetic lambda submitted to Minecraft’s cached `Download-` executor. Folder-button callbacks therefore return after scheduling the operation instead of waiting for the operating system’s folder opener.

It is not marked `CONFIRMED` because no authoritative Mojang source commit was available. The binary correlation is nevertheless unusually direct and there is no competing non-version executable change.

## Relevant implementation delta

Observed in RC1 `Blaze3D.openUri`:

```text
URI.toString()
SDLMisc.SDL_OpenURL(...)
if unsuccessful:
    SDLError.SDL_GetError()
    LOGGER.warn(...)
return
```

Observed in RC2 `Blaze3D.openUri`:

```text
Util.nonCriticalIoPool()
invokedynamic Runnable
  bootstrap: LambdaMetafactory.metafactory
  target: Blaze3D.lambda$openUri$0(URI)
TracingExecutor.execute(Runnable)
return
```

The new lambda contains the former RC1 body exactly. Its `methodCodeHash` is identical to RC1’s `openUri` hash:

```text
52268fdaf7a11bc52b100995522999e116b2f1d5834fae42744528177ef68da5
```

That demonstrates the SDL operation and failure logging were moved, not rewritten.

Relevant unchanged call chain:

```text
PackSelectionScreen “Open Pack Folder” button
  → lambda$init$0(Button)
  → Blaze3D.openPath(packDir)
  → Path.normalize()
  → Path.toUri()
  → Blaze3D.openUri(uri)
```

Executor inspection shows:

```text
Util.nonCriticalIoPool()
  → returns DOWNLOAD_POOL

DOWNLOAD_POOL
  → makeIoExecutor("Download-", true)
  → Executors.newCachedThreadPool(...)
  → TracingExecutor

TracingExecutor.execute(runnable)
  → ExecutorService.execute(wrapUnnamed(runnable))
```

Conceptual pseudocode—not recovered Mojang source:

```java
// RC1
static void openUri(URI uri) {
    openWithSdlAndLogFailure(uri);
}

// RC2
static void openUri(URI uri) {
    Util.nonCriticalIoPool().execute(
        () -> openWithSdlAndLogFailure(uri)
    );
}
```

Inferred behavioral meaning:

- RC1 invokes the operating-system opener synchronously on the calling/UI thread.
- RC2 schedules the same work on Minecraft’s cached download executor.
- Consequently, a slow or blocking `SDL_OpenURL` no longer prevents the game thread from continuing.

## Remaining uncertainty

The binaries do not expose Mojang’s source-level commit or developer intent, and the official issue page did not expose additional machine-readable details during the investigation. They also do not establish why or on which platforms SDL’s opener blocks.

They do establish that the only non-version executable RC1→RC2 change moves folder/URI opening to a background executor, directly matching MC-311782.
